# Wise funding and transfer settlement in Monedula

## Scope and evidence

This note records the implementation contract. No Wise API call, statement read, or live journal read was made during the local build. The Finances lead supplied the status enumeration from Wise documentation and the monitoring horizon below. Funding and transfer settlement are separate state machines. Only a later transfer read of `outgoing_payment_sent` establishes paid, subject to a later return.

## Baseline behavior before this change

| Surface | Observed values | Meaning for this design |
| --- | --- | --- |
| Funding response | `COMPLETED`, `PROCESSING`, `PENDING` | Wise documents `CREATED`, `COMPLETED`, and `REJECTED`. `CREATED`, `COMPLETED`, `PROCESSING`, and `PENDING` all map to handler `funding_pending`, never `sent`; `REJECTED`, missing, and unfamiliar values hold as errors. |
| Transfer lifecycle | No transfer-status read or classifier existed. | Wise's ordered status list is `incoming_payment_waiting`, `incoming_payment_initiated`, `processing`, `funds_converted`, `outgoing_payment_sent`, `bounced_back`, `charged_back`, `cancelled`, `funds_refunded`, `unknown`. Read the latest event by `occurred_at`, including rollback transitions. Only `outgoing_payment_sent` is paid. `bounced_back` is nonterminal: two observed transfers self-recovered, including one about 13 hours after an early bounce. `funds_refunded` and `cancelled` are terminal failures; `charged_back` needs operator review. Every unfamiliar status remains unresolved. |
| Handler and journal | Handler declares `sent`, `failed`, `manual_required` in [`handler_base.py`](../../execution/daemons/monedula/handler_base.py). Journal uses `intent` and `done`, plus a separate session `pending`/`settled`/`skipped`/`dropped` vocabulary. | [`payment_journal.record_outcome`](../../execution/daemons/monedula/payment_journal.py) writes `state: done` for **any** handler status, including failure. `obligation_state` then returns `done` without examining `outcome_status`. Thus `done` currently means only “a handler returned,” although callers read it as “paid.” `intent` means the external effect is unknown and already blocks replay. |

The foundation design explicitly requires a rail read at the declared terminal state and observes that a sent bank transfer may later be returned. Its drift table already identifies the funding-response shortcut. It does not establish vendor-specific Wise status mappings.

## Consumer sweep and required behavior

The handler status **`funding_pending`** requires a persisted Wise transfer ID. It means that transfer can be checked on later ticks, but payment has not been confirmed. The distinct handler status **`submission_unknown`** means transfer creation was entered but no ID was saved; the journal stays at `intent`, the operator must check Wise Activity by date, amount and reference, and Monedula cannot reconcile it automatically. Journal `funding_pending` remains distinct from both `intent` and `done` (confirmed terminal result). Every reader treats either unresolved state as **no new payment authorized**.

The approval key and settlement effects remain bound to the original approved terms. The replay hold is deliberately coarser: each new Wise intent records the stable payment profile ID. Any unresolved or invalid row for that profile holds every new obligation of the profile across edits to amount, reference, payee, due date, calendar event, prefix or handler name. An unresolved or invalid row without a usable profile ID holds all Wise profiles, with its journal key in the operator alert and manual reconciliation in Wise Activity. A valid old terminal-failure row is exempt from that global hold. The single validator is `payment_journal.classify_journal_row`; the consent, replay, session, effects, reconciliation and read-only census paths use its result.

Only the **exact historical six-field shape** (`state`, `token`, `generation`, `intent_at`, `outcome_status`, `outcome_at`) with `state: done` and `outcome_status: sent` is legacy settled. The token must be nonempty, generation a nonnegative integer (not a boolean), and both timestamps finite positive epoch numbers. The same exact old shape with `done/failed` records a finished attempt that did not pay: it holds no profile and is held only under its own obligation, including when tagged `rail: btc`; a session still keyed under the old pre-session-window key is held from being offered again, and a person clears such a session by hand. The same shape with `done/manual_required` is NOT exempt: the old writer turned any exception after the funding call into `manual_required`, so money may have moved; it is invalid and holds every Wise profile until a person checks Wise Activity. An old `intent` row with no outcome remains unknown and holds all Wise payees until a person checks Wise Activity. A stripped, mixed, extended or value-invalid row stays held; a `done/sent` tag alone never settles it. A BTC row is exempt from Wise replay only after its own historical shape validates: the same writer fields, optionally with `rail: btc`, and valid state/outcome values. A Wise-shaped row with a BTC tag is invalid, not exempt. These distinctions live in `execution/daemons/monedula/payment_journal.py::classify_journal_row`.

A modern Wise row accepts only the writer's closed field set and validates values, not only presence: positive integer transfer IDs and attempt numbers (no booleans or numeric strings), bounded identifiers and a nonempty token/profile ID, known states and statuses, finite epoch schedule and write times, and timezone-aware ISO-8601 transfer occurrence times. Its latest recorded occurrence cannot precede its own prior-attempt history. A modern sent row additionally needs nonempty handler, task, approved-terms and payment-date bindings; it releases the hold only with `state: done`, `outcome_status: sent`, a latest `outgoing_payment_sent` status, no discrepancy, durably applied effects, and a settled session when one is linked. Otherwise it remains unresolved. Later obligations are offered after confirmation. Precise obligation-level matching remains deferred to task `ent_67373ae4067dfcc0c1dd769d`.

## Proposed transition and the smaller alternative

**Recommended: persist pending, then reconcile.** The existing `obligation_key` from [`consent_email.py`](../../execution/daemons/monedula/consent_email.py) remains the one-payment identity; the approval token and request generation remain bound to its terms. Before any Wise call, write `intent` plus an attempt-scoped `customerTransactionId` derived deterministically as a UUID from that obligation and attempt number, then read back the row. The current `_create_transfer` generates a fresh UUID per call; thread the journaled ID through `WiseTransferHandler.execute` to that call. Do not regenerate it after a timeout. Persist the Wise `transfer_id` as soon as creation returns, before funding. On a lost create response, look up by the stable rail key or an adequately bounded statement window; if neither can establish absence, keep `intent` held. On an uncertain funding response, read the existing transfer; never create a new transfer or blindly repeat the funding POST.

An illustrative row in the existing journal is `obligations[<hashed-obligation>] = {state: "funding_pending", token: <short-approval-token>, generation: 7, intent_at: <time>, attempt: 1, customer_transaction_id: <stable-uuid>, transfer_id: <Wise-id>, funding_status: "COMPLETED", last_checked_at: <time>}`. Keep the present `consumed_tokens` mapping. No payee, account, or amount is added. A transfer ID absent because a response was lost leaves `state: intent`; it does not become a new attempt. `record_funding_pending` rejects missing intent, mismatched IDs, and invalid transitions, and reads back fields that control retry. Reconcile **all** unresolved Wise entries independently of the calendar window. A confirmed `outgoing_payment_sent` writes a checked `done/sent` outcome, then settles the session and updates the task. Task, profile, due-date and session effects require the latest recorded transfer status by `occurred_at` to be `outgoing_payment_sent`; a historical `sent` outcome alone is insufficient. When a check is due, read the transfer before applying recovered effects. Other statuses and read errors keep payment unresolved. A first `bounced_back` sets a next-day check; a persistent bounce remains unresolved because Wise can self-recover. A replacement requires a **new** operator approval under the same obligation, appended as the next numbered attempt, only after a transfer read confirms `funds_refunded` or `cancelled`. Never resend automatically. A later return after `sent` raises a discrepancy alert without deleting the original confirmation or rewriting already applied effects.

This holds repeat attempts because every entrance checks the durable obligation row **before** Wise submission, the attempt key is recorded before create, and no pending/unknown state is retry-eligible. The key is not assumed to make create-transfer idempotent. A crash before intent write cannot have contacted Wise; a crash after intent write enters reconciliation. A failed journal update or partial rail read holds payment. A daemon tick takes an exclusive advisory lock on the existing first-use marker to serialize journal writers; direct external writes still require the same discipline.

**Minimal alternative: wait inside the handler for `outgoing_payment_sent`.** Keep the current `intent` row and its consumed token while polling the **transfer endpoint**, never the funding response, with a bounded wait. Only return `sent` on confirmed state; on timeout, read failure, `incoming_payment_waiting`, or first `bounced_back`, return no final result and leave `intent` held for later manual reconciliation. Use the same stable obligation-derived `customerTransactionId`, and persist/adopt the transfer ID in the journal if possible. A replay sees `intent` and never funds again, so the safety argument is sound only if the handler does **not** convert the timeout into `manual_required` with instructions to pay by hand. The row remains `intent` until confirmation, then `done/sent`. This is fewer state transitions but cannot settle a transfer that completes after the process exits without an external/manual read; a long wait also ties up a daemon tick. Prefer the durable pending state and bounded reconciliation.

## Test and migration plan

Use mocked Wise GET/POST responses only. Parametrize funding `CREATED`, `COMPLETED`, `PROCESSING`, `PENDING`, `REJECTED`, missing and unexpected statuses; none may produce paid task effects or a SENT alert. Mock transfer reads for every listed status, rollback ordering by `occurred_at`, first bounce and self-recovery, later return after sent, malformed body, 401/5xx, timeout, and incomplete status history. Assert the visible effects on the default approval and Telegram break-glass paths. Use `tmp_path` for every journal and first-use marker test; never point a test at the daemon's journal path. Test failed writes/read-backs and crash boundaries around create, funding and final-state write. Replay the same approval after a pending result, restart, and lost funding response: create and fund must not run a second time. Assert task and session updates once after confirmed settlement. BTC's `sent` contract stays unchanged.

For existing `done/sent` rows, produce a **read-only discrepancy report**: enumerate the journal's hashed obligations and any available Wise transfer identifiers from associated task notes or other existing records; cross-check against Wise statements over a documented complete window. The current journal does **not** store a Wise transfer ID, so a row without a defensible match must be reported `unmatched`, not assumed paid. Report `confirmed sent`, `returned/bounced`, `still pending`, and `unmatched` with evidence and statement coverage, without editing the journal or first-use marker. The operator reviews discrepancies against Wise's own statement and the obligation, decides whether any manual payment is needed, and authorizes any replacement separately. A report alone never unlocks a retry.

## Recovery and compatibility

### Recovery after a failure before transfer creation

The journal records `failed/not_submitted` only when transfer creation was never
entered. The operator alert and consent copy say “not submitted; no payment was
made.” That row remains held on ordinary ticks. A fresh, independently verified
operator approval may reserve attempt 2 on the **same obligation** through
`record_approved_replacement_intent`, preserving the first attempt and consuming
the new approval token. The live consent adapters do not yet issue or execute a
replacement attempt; the Finances lead must complete and verify that adapter
before a retry is available. A create call that was entered, even if it raised,
remains `intent` with unknown outcome and cannot take this release path. A
rejected funding response leaves an existing transfer ID held for reconciliation;
it is never represented as “not submitted.”

One-off obligations use the invoice due date and profile terms, not the tick
date. An unresolved row written under the old tick-date key is held by its
journaled profile ID, or globally if no usable profile ID was recorded; the
old row is never re-keyed or discarded.
After confirmed settlement, the profile is reloaded so an archived one-off is
not offered again in that tick.

### Behaviour on other rails

`obligation_state` maps an exact legacy `done/failed` row to `failed`, including a BTC-tagged row. Its own
obligation (and a session under the same old key) remains held; it creates no global Wise hold. A legacy
`done/manual_required` row is invalid and holds every Wise profile (money may have moved). Other BTC outcomes
retain their existing classification.

### Known limits

- The approved-replacement reservation exists in the journal, but neither live
  consent adapter can yet produce an attempt-specific replacement approval.
  Terminal failures and `not_submitted` attempts stay held until that route is
  built and verified.
- A Wise transfer still unresolved after two calendar days raises a deduped
  alert. This is a wall-clock threshold, not a business-day calculation.
- Terminally failed transfers are not read on every tick. Any later vendor
  status change needs a separate operator-initiated review.
- A new invoice for a profile with any unresolved Wise row is held even if it
  is a distinct obligation. An unresolved or invalid row with no usable
  profile ID holds all Wise invoices until manual reconciliation. This deliberate scope cut will be
  narrowed only by the deferred identity work.
- Routine confirmed-transfer monitoring ends after the existing 30-day window;
  a later return requires a separate statement or transfer read.

## Risks and decisions

- **Wise status contract and lookup coverage:** verify the transfer-status endpoint, exact terminal values, pagination, and statement retention with primary Wise documentation before coding. Until verified, classify unfamiliar values as unresolved and hold.
- **Funding idempotency seam TODO:** confirm with a Wise sandbox test or Wise support whether `customerTransactionId` can be looked up and whether create-transfer accepts it as an idempotency key; also confirm the behavior of a second funding call. Do not rely on either behavior in the meantime. Never repeat an ambiguous funding call; read/adopt or escalate.
- **Later returns:** after `outgoing_payment_sent`, re-check the next day, then daily through three business days, then weekly through 30 days (`MONITOR_DAYS = 30`, `FIRST_BUSINESS_DAYS = 3` in `wise_reconcile.py`). After that the row is final; a later observed return still raises a discrepancy without rewriting historical confirmation.
- **Replacement authority:** a failed/returned transfer is not a reusable approval. A new operator approval tied to the same obligation starts a new numbered attempt only after a read confirms `funds_refunded` or `cancelled`; there is no automatic resend.
- **Replacement integration still open:** the journal has a numbered-attempt reservation API, but the live consent routes do not yet issue an attempt-specific approval for the same obligation. Keep the failed obligation held until that route is implemented and verified.
- **Late-return detection limit:** routine checks end after 30 days. A return observed by a later read raises a discrepancy; no independent later-return feed is wired.
- **Legacy rows without transfer IDs:** matching may be ambiguous. Recommend an operator-reviewed read-only report; do not infer paid or auto-retry from journal `sent` alone.
