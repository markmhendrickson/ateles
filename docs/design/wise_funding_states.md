# Wise funding and transfer settlement in Monedula

## Scope and evidence

This note designs a change; it does not change payment behavior. It is based on repository code, tests, and [`docs/foundation/payments.md`](../foundation/payments.md). No Wise API call, statement read, or live journal read was made. The repository does not contain a complete Wise status enumeration or prove the semantics of every Wise status. In particular, the funding response and the transfer lifecycle must be treated as separate state machines. The policy supplied for this investigation is to count a transfer paid only when a later transfer read confirms `outgoing_payment_sent`, and to re-check a `bounced_back` transfer the next day before deciding that a replacement is needed. Those named transfer statuses and the timing rule could not be confirmed from the repository's Wise handler or tests; verify the exact vendor status contract before implementation, without changing the conservative hold rule meanwhile.

## States the current code recognizes

| Surface | Observed values | Meaning for this design |
| --- | --- | --- |
| Funding response | `COMPLETED`, `PROCESSING`, `PENDING` | [`_execute_wise_transfer`](../../execution/daemons/monedula/handlers/wise_transfer.py) maps **all three** to handler `sent`. `COMPLETED` indicates completion of the funding step only. `PROCESSING` and `PENDING` are pending even for that step. None establishes terminal transfer success. Missing or any other value raises; [`WiseTransferHandler.execute`](../../execution/daemons/monedula/handlers/wise_transfer.py) catches the exception as `manual_required`, even if a transfer was already created or funded. |
| Transfer lifecycle | No transfer-status read or classifier exists in the handler. The investigation's target states are `incoming_payment_waiting`, `outgoing_payment_sent`, and `bounced_back`. | Treat `incoming_payment_waiting` and all unclassified states as pending/unknown. A confirmed `outgoing_payment_sent` is the paid criterion. A first `bounced_back` is **not** permission to resend: hold and read again the next day; a persistent confirmed return is a failed payment needing review. A later return after `outgoing_payment_sent` must reopen the obligation for investigation without erasing the earlier confirmation. Other terminal-failure names cannot be established from this checkout. |
| Handler and journal | Handler declares `sent`, `failed`, `manual_required` in [`handler_base.py`](../../execution/daemons/monedula/handler_base.py). Journal uses `intent` and `done`, plus a separate session `pending`/`settled`/`skipped`/`dropped` vocabulary. | [`payment_journal.record_outcome`](../../execution/daemons/monedula/payment_journal.py) writes `state: done` for **any** handler status, including failure. `obligation_state` then returns `done` without examining `outcome_status`. Thus `done` currently means only “a handler returned,” although callers read it as “paid.” `intent` means the external effect is unknown and already blocks replay. |

The foundation design explicitly requires a rail read at the declared terminal state and observes that a sent bank transfer may later be returned. Its drift table already identifies the funding-response shortcut. It does not establish vendor-specific Wise status mappings.

## Consumer sweep and required behavior

The proposed handler status is **`funding_pending`**. It means a Wise transfer exists or funding may have started, but payment has not been confirmed. A new journal `funding_pending` state must be distinct from both `intent` (unknown submission outcome) and `done` (confirmed terminal result). Every reader below must treat either unresolved state as **no new payment authorized**.

## Proposed transition and the smaller alternative

**Recommended: persist pending, then reconcile.** The existing `obligation_key` from [`consent_email.py`](../../execution/daemons/monedula/consent_email.py) remains the one-payment identity; the approval token and request generation remain bound to its terms. Before any Wise call, write `intent` plus an attempt-scoped `customerTransactionId` derived deterministically as a UUID from that obligation and attempt number, then read back the row. The current `_create_transfer` generates a fresh UUID per call; thread the journaled ID through `WiseTransferHandler.execute` to that call. Do not regenerate it after a timeout. Persist the Wise `transfer_id` as soon as creation returns, before funding. On a lost create response, look up by the stable rail key or an adequately bounded statement window; if neither can establish absence, keep `intent` held. On an uncertain funding response, read the existing transfer; never create a new transfer or blindly repeat the funding POST.

An illustrative row in the existing journal is `obligations[<hashed-obligation>] = {state: "funding_pending", token: <short-approval-token>, generation: 7, intent_at: <time>, attempt: 1, customer_transaction_id: <stable-uuid>, transfer_id: <Wise-id>, funding_status: "COMPLETED", last_checked_at: <time>}`. Keep the present `consumed_tokens` mapping. No payee, account, or amount is added. A transfer ID absent because a response was lost leaves `state: intent`; it does not become a new attempt. `record_funding_pending` must reject missing intent, mismatched IDs, and invalid transitions, and read back all fields that control retry. Add a reconciliation pass over **all** unresolved Wise entries, independent of today's calendar trigger. A confirmed `outgoing_payment_sent` writes a checked `done/sent` outcome and then settles the session and updates the task. `incoming_payment_waiting`, unknown values, and read errors keep pending. First `bounced_back` records the observed return and a next-day check due time, still blocking any new transfer. If still returned on the next day, mark a confirmed failure for operator review; any new attempt requires a fresh approval and an appended attempt within the same obligation row, after confirming the first cannot pay. A later return after `sent` adds a reversal observation and reopens investigation without deleting the original confirmation.

This prevents two payments because every entrance checks the durable obligation row **before** Wise submission, every repeat uses the same attempt key to *read/adopt*, and no pending/unknown state is retry-eligible. A crash before intent write cannot have contacted Wise; a crash after intent write can only enter reconciliation. A failed journal update or partial rail read holds the payment. The present read/write scheme is not a cross-process lock; implementation must also establish single-writer serialization or an atomic reservation for concurrent ticks before claiming this is an exactly-once guarantee.

**Minimal alternative: wait inside the handler for `outgoing_payment_sent`.** Keep the current `intent` row and its consumed token while polling the **transfer endpoint**, never the funding response, with a bounded wait. Only return `sent` on confirmed state; on timeout, read failure, `incoming_payment_waiting`, or first `bounced_back`, return no final result and leave `intent` held for later manual reconciliation. Use the same stable obligation-derived `customerTransactionId`, and persist/adopt the transfer ID in the journal if possible. A replay sees `intent` and never funds again, so the safety argument is sound only if the handler does **not** convert the timeout into `manual_required` with instructions to pay by hand. The row remains `intent` until confirmation, then `done/sent`. This is fewer state transitions but cannot settle a transfer that completes after the process exits without an external/manual read; a long wait also ties up a daemon tick. Prefer the durable pending state and bounded reconciliation.

## Test and migration plan

Use mocked Wise GET/POST responses only. Parametrize funding `COMPLETED`, `PROCESSING`, `PENDING`, missing and unexpected statuses; none may produce paid task effects or a SENT alert. Mock transfer reads for waiting, sent, first bounce, next-day persistent bounce, later return after sent, malformed body, 401/5xx, timeout, and paginated/incomplete statement search. Assert the *visible effect*: the obligation stays payable only after confirmed settlement or reviewed replacement, and no pending result says “paid” or “pay by hand.” Test both default approval and Telegram break-glass shapes. Use `tmp_path` for every journal test, including its first-use marker; never point a test at the daemon's journal path. Test failed writes/read-backs and crash boundaries around create, funding and final-state write. Replay the same approval after a pending result, after restart, and after a lost funding response: `_create_transfer` and `_fund_transfer` must not run a second time, and the consumed token remains bound. Assert a confirmed outcome updates the recurring due date or one-off archive **once**. Keep tests for BTC's existing `sent` contract. Update the README and handler contract in the implementation PR.

For existing `done/sent` rows, produce a **read-only discrepancy report**: enumerate the journal's hashed obligations and any available Wise transfer identifiers from associated task notes or other existing records; cross-check against Wise statements over a documented complete window. The current journal does **not** store a Wise transfer ID, so a row without a defensible match must be reported `unmatched`, not assumed paid. Report `confirmed sent`, `returned/bounced`, `still pending`, and `unmatched` with evidence and statement coverage, without editing the journal or first-use marker. The operator reviews discrepancies against Wise's own statement and the obligation, decides whether any manual payment is needed, and authorizes any replacement separately. A report alone never unlocks a retry.

## Risks and decisions

- **Wise status contract and lookup coverage:** verify the transfer-status endpoint, exact terminal values, pagination, and statement retention with primary Wise documentation before coding. Until verified, classify unfamiliar values as unresolved and hold.
- **Funding idempotency seam:** confirm whether the rail can look up `customerTransactionId` and how duplicate funding requests behave. Regardless, never repeat an ambiguous funding call; use read/adopt or escalate.
- **Later returns:** a `sent` state may be reversed. Keep monitoring the declared return window and raise a new discrepancy without rewriting the historical confirmation; the Finances lead should choose the monitoring horizon from the rail contract.
- **Replacement authority:** a failed/returned transfer is not a reusable approval. Recommend a new operator approval tied to the same obligation and a new numbered attempt only after the earlier transfer is proven unable to pay.
- **Legacy rows without transfer IDs:** matching may be ambiguous. Recommend an operator-reviewed read-only report; do not infer paid or auto-retry from journal `sent` alone.
