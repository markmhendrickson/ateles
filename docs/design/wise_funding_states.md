# Wise funding and transfer settlement in Monedula

## Scope and evidence

This note records the implementation contract. No Wise API call, statement read, or live journal read was made during the local build. The Finances lead supplied the status enumeration from Wise documentation and the monitoring horizon below. Funding and transfer settlement are separate state machines. Only a later transfer read of `outgoing_payment_sent` establishes paid, subject to a later return.

## Baseline behavior before this change

| Surface | Observed values | Meaning for this design |
| --- | --- | --- |
| Funding response | `COMPLETED`, `PROCESSING`, `PENDING` | Wise documents `CREATED`, `COMPLETED`, and `REJECTED`. `CREATED`, `COMPLETED`, `PROCESSING`, and `PENDING` all map to handler `funding_pending`, never `sent`; `REJECTED`, missing, and unfamiliar values hold as errors. |
| Transfer lifecycle | No transfer-status read or classifier existed. | Wise's ordered status list is `incoming_payment_waiting`, `incoming_payment_initiated`, `processing`, `funds_converted`, `outgoing_payment_sent`, `bounced_back`, `charged_back`, `cancelled`, `funds_refunded`, `unknown`. Read the latest event by `occurred_at`, including rollback transitions. Only `outgoing_payment_sent` is paid. `bounced_back` is nonterminal: two observed transfers self-recovered, including one about 13 hours after an early bounce. `funds_refunded` and `cancelled` are terminal failures; `charged_back` needs operator review. Every unfamiliar status remains unresolved. |
| Handler and journal | Handler declares `sent`, `failed`, `manual_required` in [`handler_base.py`](../../execution/daemons/monedula/handler_base.py). Journal uses `intent` and `done`, plus a separate session `pending`/`settled`/`skipped`/`dropped` vocabulary. | [`payment_journal.record_outcome`](../../execution/daemons/monedula/payment_journal.py) writes `state: done` for **any** handler status, including failure. `obligation_state` then returns `done` without examining `outcome_status`. Thus `done` currently means only “a handler returned,” although callers read it as “paid.” `intent` means the external effect is unknown and already blocks replay. |

The foundation design explicitly requires a rail read at the declared terminal state and observes that a sent bank transfer may later be returned. Its drift table already identifies the funding-response shortcut. It does not establish vendor-specific Wise status mappings.

## Consumer sweep and required behavior

The proposed handler status is **`funding_pending`**. It means a Wise transfer exists or funding may have started, but payment has not been confirmed. A new journal `funding_pending` state must be distinct from both `intent` (unknown submission outcome) and `done` (confirmed terminal result). Every reader below must treat either unresolved state as **no new payment authorized**.

| Consumer | Current `sent` behavior | Risk if only the handler changes; required `funding_pending` behavior |

## Proposed transition and the smaller alternative

**Recommended: persist pending, then reconcile.** The existing `obligation_key` from [`consent_email.py`](../../execution/daemons/monedula/consent_email.py) remains the one-payment identity; the approval token and request generation remain bound to its terms. Before any Wise call, write `intent` plus an attempt-scoped `customerTransactionId` derived deterministically as a UUID from that obligation and attempt number, then read back the row. The current `_create_transfer` generates a fresh UUID per call; thread the journaled ID through `WiseTransferHandler.execute` to that call. Do not regenerate it after a timeout. Persist the Wise `transfer_id` as soon as creation returns, before funding. On a lost create response, look up by the stable rail key or an adequately bounded statement window; if neither can establish absence, keep `intent` held. On an uncertain funding response, read the existing transfer; never create a new transfer or blindly repeat the funding POST.

An illustrative row in the existing journal is `obligations[<hashed-obligation>] = {state: "funding_pending", token: <short-approval-token>, generation: 7, intent_at: <time>, attempt: 1, customer_transaction_id: <stable-uuid>, transfer_id: <Wise-id>, funding_status: "COMPLETED", last_checked_at: <time>}`. Keep the present `consumed_tokens` mapping. No payee, account, or amount is added. A transfer ID absent because a response was lost leaves `state: intent`; it does not become a new attempt. `record_funding_pending` rejects missing intent, mismatched IDs, and invalid transitions, and reads back fields that control retry. Reconcile **all** unresolved Wise entries independently of the calendar window. A confirmed `outgoing_payment_sent` writes a checked `done/sent` outcome, then settles the session and updates the task. Other statuses and read errors keep payment unresolved. A first `bounced_back` sets a next-day check; a persistent bounce remains unresolved because Wise can self-recover. A replacement requires a **new** operator approval under the same obligation, appended as the next numbered attempt, only after a transfer read confirms `funds_refunded` or `cancelled`. Never resend automatically. A later return after `sent` raises a new discrepancy alert without deleting the original confirmation.

This holds repeat attempts because every entrance checks the durable obligation row **before** Wise submission, the attempt key is recorded before create, and no pending/unknown state is retry-eligible. The key is not assumed to make create-transfer idempotent. A crash before intent write cannot have contacted Wise; a crash after intent write enters reconciliation. A failed journal update or partial rail read holds payment. A daemon tick takes an exclusive advisory lock on the existing first-use marker to serialize journal writers; direct external writes still require the same discipline.

**Minimal alternative: wait inside the handler for `outgoing_payment_sent`.** Keep the current `intent` row and its consumed token while polling the **transfer endpoint**, never the funding response, with a bounded wait. Only return `sent` on confirmed state; on timeout, read failure, `incoming_payment_waiting`, or first `bounced_back`, return no final result and leave `intent` held for later manual reconciliation. Use the same stable obligation-derived `customerTransactionId`, and persist/adopt the transfer ID in the journal if possible. A replay sees `intent` and never funds again, so the safety argument is sound only if the handler does **not** convert the timeout into `manual_required` with instructions to pay by hand. The row remains `intent` until confirmation, then `done/sent`. This is fewer state transitions but cannot settle a transfer that completes after the process exits without an external/manual read; a long wait also ties up a daemon tick. Prefer the durable pending state and bounded reconciliation.

## Test and migration plan

Use mocked Wise GET/POST responses only. Parametrize funding `CREATED`, `COMPLETED`, `PROCESSING`, `PENDING`, `REJECTED`, missing and unexpected statuses; none may produce paid task effects or a SENT alert. Mock transfer reads for every listed status, rollback ordering by `occurred_at`, first bounce and self-recovery, later return after sent, malformed body, 401/5xx, timeout, and incomplete status history. Assert the visible effects on the default approval and Telegram break-glass paths. Use `tmp_path` for every journal and first-use marker test; never point a test at the daemon's journal path. Test failed writes/read-backs and crash boundaries around create, funding and final-state write. Replay the same approval after a pending result, restart, and lost funding response: create and fund must not run a second time. Assert task and session updates once after confirmed settlement. BTC's `sent` contract stays unchanged.

For existing `done/sent` rows, produce a **read-only discrepancy report**: enumerate the journal's hashed obligations and any available Wise transfer identifiers from associated task notes or other existing records; cross-check against Wise statements over a documented complete window. The current journal does **not** store a Wise transfer ID, so a row without a defensible match must be reported `unmatched`, not assumed paid. Report `confirmed sent`, `returned/bounced`, `still pending`, and `unmatched` with evidence and statement coverage, without editing the journal or first-use marker. The operator reviews discrepancies against Wise's own statement and the obligation, decides whether any manual payment is needed, and authorizes any replacement separately. A report alone never unlocks a retry.

## Risks and decisions

- **Wise status contract and lookup coverage:** verify the transfer-status endpoint, exact terminal values, pagination, and statement retention with primary Wise documentation before coding. Until verified, classify unfamiliar values as unresolved and hold.
- **Funding idempotency seam TODO:** confirm with a Wise sandbox test or Wise support whether `customerTransactionId` can be looked up and whether create-transfer accepts it as an idempotency key; also confirm the behavior of a second funding call. Do not rely on either behavior in the meantime. Never repeat an ambiguous funding call; read/adopt or escalate.
- **Later returns:** after `outgoing_payment_sent`, re-check the next day, then daily through three business days, then weekly through 30 days (`MONITOR_DAYS = 30`, `FIRST_BUSINESS_DAYS = 3` in `wise_reconcile.py`). After that the row is final; a later observed return still raises a discrepancy without rewriting historical confirmation.
- **Replacement authority:** a failed/returned transfer is not a reusable approval. A new operator approval tied to the same obligation starts a new numbered attempt only after a read confirms `funds_refunded` or `cancelled`; there is no automatic resend.
- **Legacy rows without transfer IDs:** matching may be ambiguous. Recommend an operator-reviewed read-only report; do not infer paid or auto-retry from journal `sent` alone.
